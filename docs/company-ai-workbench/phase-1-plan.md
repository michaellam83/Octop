# 第一阶段实施方案

## 1. 阶段目标

第一阶段不是完成完整的企业工作台，而是完成一个可以真实启动验证的最小闭环：

```text
管理员初始化 Octop
        ↓
创建“通联智多星”逻辑模型配置
        ↓
创建“通联发仔”系统专家模板
        ↓
管理员创建公司用户并配置用户级 ZDX API Key
        ↓
系统自动创建该用户的“通联发仔”专家
        ↓
用户通过该专家调用智多星
        ↓
管理员更新模板，关联用户实例自动同步并重新加载
```

完成本阶段后，使用两名测试用户进行 Key 隔离、模板同步、专家锁定和基础业务调用验证。

## 2. 第一阶段范围

### 2.1 初始化和模型配置

初始化流程只为“通联发仔”托管模板写入一份模型配置，不创建智多星 Provider：

```text
模型类型：tonglian_zdx
Base URL：https://ai.allinpay.com/v1/
模型：auto
凭据范围：current_user
调用模式：direct
```

这份配置只属于“通联发仔”，不进入普通 Provider 列表、普通模型池或 Harness 模型工厂。

智多星侧已经确认以下调用约束：

- 当智多星需要调用后端业务或内部系统时，必须传递 `chatBizOptions.userid`；
- `userid` 用于业务权限和数据可读范围校验；
- `ZDX_API_KEY` 与 `userid` 是绑定关系，智多星会校验二者是否匹配；
- 适配器对每次请求统一注入当前用户身份，不允许使用其他用户或管理员 Key 回退。

第一阶段采用以下运行方式：

- 对外显示仍然是“通联智多星”；
- 每次调用按当前登录用户解析对应的 ZDX Key 和 userid；
- 直连请求不向 Harness 转发 tools、tool_choice、普通 Provider 或 Skill 调用上下文；
- 没有用户凭据时禁止回退到管理员 Key；
- 没有配置凭据的用户显示“待管理员开通”，而不是把 Key 错误归因给其他用户。
- 对“通联发仔”发往智多星的请求，由适配层统一携带当前用户的 `userid`；涉及后端业务或系统调用时不得省略该字段。

### 2.2 智多星直连适配

“通联发仔”使用 Octop 自有的直连适配器：

- 请求地址和模型类型来自托管模板的 `managed_model`；
- API Key 从当前登录用户的加密凭据中解析；
- `chatBizOptions.userid` 始终使用当前用户配置的真实 OA username；
- 请求只发送智多星需要的 messages、model、stream 和 chatBizOptions；
- 网页对话和 IM 对话都绕过普通 Provider、Harness 模型工厂、MCP 和 Skill 调用链；
- 其他普通 Agent 仍使用原有 Harness/Provider 路径。

### 2.3 “通联发仔”专家模板

新增系统模板：

```text
template_id：tonglian-fazai
显示名称：通联发仔
可见性：admin_only
模板模型：通联智多星
允许模型：仅通联智多星
调用方式：用户级智多星直连
基础文件：沿用 general-assistant 的通用文件结构
```

模板需要具备独立的版本号。模板更新的内容包括：

- `SOUL.md`；
- 系统提示词；
- 通用预设 Markdown；
- `managed_model` 直连模型配置和允许模型范围；
- 欢迎语和展示信息。

模板更新不能覆盖用户实例中的：

- 对话历史；
- 记忆；
- 用户个人文件；
- 用户工作区中非系统管理的内容。

### 2.4 用户级智多星凭据

管理员为用户配置：

```text
ZDX_USERID：管理员录入的真实 OA username
ZDX_API_KEY：管理员录入，系统加密保存
```

本地改造和验证阶段不接入 OA / 企业微信扫码登录。管理员需要按照公司现行规则手工录入真实 OA username。username 规则为：

- 中文姓名转为小写拼音；
- 姓名较短时使用姓名拼音全拼；
- 姓名较长时使用姓氏全拼加名字首字母；
- 组合结果冲突时追加数字，保证 username 全局唯一。

系统不在第一阶段自行重新生成 username，也不使用显示姓名替代 username。管理员录入的值直接作为 `ZDX_USERID`，并在保存时做必要的格式校验和唯一性检查。

实现上，第一阶段建议直接把真实 OA username 作为 Octop 用户的 `username`，这样可以复用现有用户唯一约束和后续登录映射。若后续业务要求本地登录名与 OA username 分离，则新增独立且唯一的 `oa_username` 字段；不能在凭据服务中额外保存一份没有唯一约束的身份字符串。

用户端只显示凭据状态：

- 未配置；
- 已配置；
- 调用失败或已失效。

用户不能：

- 查看明文 Key；
- 修改 `ZDX_USERID`；
- 将 Key 绑定到其他用户；
- 通过普通环境变量或工作区文件读取 Key。

实现上优先复用现有 `SecretRepo` 和安装级 Fernet 密钥，增加一个用户级 ZDX 凭据服务进行命名空间管理，例如：

```text
zdx.api_key.user.<user_id>
```

管理员配置接口只提供设置、替换、清除和脱敏状态查询。

### 2.5 自动创建托管 Agent

每个用户最多创建一个“通联发仔”实例。用户实例使用：

```text
name：通联发仔
agent_id：沿用 Octop 自动生成的短 ID
template_name：tonglian-fazai
managed_type：tonglian_fazai
config_locked：true
template_version：当前模板版本
```

不建议把 OA username 拼入 Agent ID。Agent ID 会用于数据库、工作区目录、API 路径和运行时注册，沿用 Octop 的随机短 ID 可以避免路径、变更和隐私问题。

自动创建必须幂等，至少覆盖：

- 管理员手工创建用户；
- SSO 自动创建用户；
- 邀请注册用户；
- 初始化创建的首个管理员；
- 服务重启和重复执行初始化。

### 2.6 托管 Agent 的权限和界面

用户端只显示：

- 对话；
- 启用 / 停用开关；
- 必要的运行状态和凭据状态。

隐藏并在后端拒绝：

- 编辑；
- 删除；
- 修改名称；
- 修改模型；
- 修改系统提示词；
- 修改 Skill、插件、工具和 MCP；
- 修改工作区、人格、记忆、头像；
- 手工 Reload；
- 发布、共享和复制配置。

前端隐藏只改善使用体验，后端必须依据 `managed_type` 或 `config_locked` 再次校验。

启用 / 停用沿用 Octop 当前 Agent lifecycle：

```text
启用：start
停用：stop
```

用户不需要看到单独的“重新加载配置”按钮。模板更新由系统触发运行中的 Agent reload，停用的 Agent 在下次启用时加载最新模板版本。

### 2.7 管理员模板更新和同步

管理员更新“通联发仔”模板时执行：

1. 保存模板内容和新版本号；
2. 查找所有 `managed_type=tonglian_fazai` 的用户 Agent；
3. 同步模板所有权范围内的文件和配置；
4. 更新用户 Agent 的 `template_version`；
5. 对正在运行的实例执行 reload；
6. 对已停用实例只保存新配置，下一次启用时加载。

同步必须有审计日志，至少记录：

- 操作管理员；
- 模板版本；
- 受影响用户数；
- 成功、失败和待下次启动的实例数。

### 2.8 安全修复

第一阶段必须同时修复 Provider Key 暴露问题：

- 普通用户 Provider API 不返回明文 Key；
- 管理员也只看到脱敏 Key；
- 用户级 ZDX Key 不放入全局环境配置；
- 不写入 Agent 工作区；
- 不出现在日志、异常、请求 dump 和前端响应中；
- 失败信息不能把用户 Key 或完整 Authorization 头带出来。

智多星身份校验也必须作为安全边界处理：

- 请求使用当前 Agent 所属用户的 OA username 作为 `userid`；
- 请求使用同一用户对应的 ZDX Key；
- Key 与 username 不匹配时，调用必须失败，不能尝试其他用户 Key；
- 不允许由聊天内容、Skill 文本或用户请求覆盖系统注入的 `userid`；
- `userid` 不能由普通用户在 Agent 配置中编辑。

## 3. 暂不纳入第一阶段

以下内容先不纳入本轮，以免影响核心闭环验证：

- 公司 Logo、Icon、主题色和整体视觉改造；
- OA / 企业微信扫码登录和域名部署；
- 自动从智多星获取用户 Key；
- OA、审批、HR、邮箱、工单、Redmine 等业务系统接入；
- 智多星 MCP 在 Octop 外部直接暴露；
- 用户端完整功能屏蔽的全面重构；
- 复杂的企业管理员组织架构和批量导入；
- 多级审批、额度、部门级模型策略。

第一阶段验证使用现有登录方式和管理员创建用户接口。管理员为测试用户手工录入真实 OA username；后续接入 OA / 企业微信扫码登录时，再把登录返回的 username 映射到同一用户字段，不改变智多星凭据路由和 Agent 模型约束。

## 4. 建议的实现顺序

### Step 1：数据库和领域模型

- 增加 Agent 托管字段：`managed_type`、`config_locked`、`template_version`；
- 增加同一用户同一托管类型唯一约束；
- 扩展 `AgentRow`、`AgentRepo`、共享服务注册；
- 增加模板版本和同步状态的领域服务；
- 确认 SQLite、PostgreSQL 两套迁移脚本保持一致。

验证：迁移可重复执行，旧数据库可升级，普通 Agent 行为不变。

### Step 2：托管模型配置和直连适配

- 增加“通联发仔”托管模型元数据；
- 增加用户级凭据解析和智多星直连客户端；
- 固定 Base URL、模型类型和 `chatBizOptions.userid` 注入规则；
- 确保直连请求不携带 Octop tools、tool_choice 或普通 Provider 配置。

验证：通联发仔不进入普通 Provider/Skill 链路，其他模型和插件行为不受影响。

### Step 3：用户凭据和模型路由

- 增加管理员配置用户 ZDX Key 的后端服务和 API；
- 加密保存，返回脱敏状态；
- 从当前用户解析 `ZDX_USERID`；
- 让“通联发仔”使用当前用户 Key；
- 禁止使用全局管理员 Key 作为员工流量回退；
- 用户没有 Key 时返回可识别的待开通状态。

第一阶段不改造 `harness-agent` 的全局模型工厂，而是在 Octop 的通联业务入口增加独立直连适配器，避免用户级凭据进入 Provider 缓存和普通 Agent 运行时。

验证：两个用户并发调用时，日志、请求和智多星侧身份都不能串用。

### Step 4：模板和用户生命周期

- 创建 `tonglian-fazai` 模板；
- 将用户创建、SSO 创建和邀请创建统一接入自动 provisioning；
- 保证重复调用不会产生第二个托管 Agent；
- 模板更新后批量同步并刷新运行时；
- 用户删除时清理托管 Agent 和用户级凭据。

验证：重复登录、重复创建、服务重启、模板升级均保持幂等。

### Step 5：权限和最小 UI

- Agent API 对托管实例增加修改、删除、插件、Skill、工作区等后端拦截；
- API 返回托管标识和可用操作集合；
- 用户端隐藏不允许的按钮；
- 管理端提供用户 ZDX Key 配置状态和模板更新入口；
- 用户端仅保留通联发仔对话、启用 / 停用和状态展示。

验证：直接调用隐藏 API 也无法修改或删除托管实例。

### Step 6：回归和启动验证

- 运行数据库、Agent、Provider、插件、用户、API 和 Dashboard 测试；
- 启动本地服务；
- 使用两个测试用户完成验证清单；
- 记录智多星接口返回、ZDX_USERID、模型链路和错误日志；
- 再决定是否进入 OA 登录和视觉改造。

## 5. 预计影响范围

这是中高工作量的后端改造，不是单纯增加一个配置项。按当前代码结构，预估影响如下：

| 区域 | 预估影响 | 工作量 | 说明 |
|---|---:|---|---|
| 数据库迁移 | 2 个迁移脚本，可能增加 1 个索引 | 中 | 同时维护 SQLite / PostgreSQL |
| Agent Repo / Manager | 5-8 个文件 | 中高 | 托管字段、生命周期、自动同步、锁定 |
| 用户生命周期 | 3-5 个文件 | 中 | 管理员创建、SSO、邀请和初始化都要接入 |
| Provider / 凭据 | 6-10 个文件 | 高 | 用户级密钥路由是最大风险点 |
| Expert Catalog / 模板 | 3-6 个文件 | 中高 | admin-only、版本、批量同步 |
| ZDX 原生插件 | 8-15 个文件 | 中 | 主要是目录包装、配置规范和脚本适配 |
| API 路由 | 5-8 个文件 | 中 | 用户凭据、专家权限、Provider 脱敏 |
| Dashboard 最小改造 | 5-8 个文件 | 中 | 托管 Agent 操作收敛、管理员配置界面 |
| 测试 | 10-16 个测试文件或测试模块 | 中高 | 重点是凭据隔离和越权验证 |
| 文档与迁移说明 | 2-4 个文件 | 低 | 初始化、部署、验证和运维说明 |

综合估计：

- 直接触及约 30-50 个已有或新增文件；
- 新增约 2,000-4,000 行代码和测试的可能性较高；
- 不包含 Dashboard 构建产物、品牌资源和后续业务系统集成；
- 如果修改 `harness-agent` 依赖以支持原生用户级 API Key，工作量和维护边界会进一步扩大；
- 如果采用 Octop 内部用户级 Provider 适配，第一阶段更容易快速验证，但长期需要考虑替换为更清晰的模型凭据解析接口。

## 6. 第一阶段完成标准

只有同时满足下面条件，才进入内部验证：

1. 新初始化实例自动存在“通联智多星”和“通联发仔”模板；
2. 管理员创建用户后，用户自动拥有唯一的“通联发仔”；
3. 用户可以通过“通联发仔”完成至少一条智多星知识库问答和一条内部业务查询；
4. 两个用户的 `ZDX_USERID` 和 Key 在并发调用时不会串用；
5. 没有用户凭据时不会回退到全局 Key；
6. 用户不能删除、编辑、换模型或修改托管 Agent；
7. 用户只能通过启用 / 停用控制运行状态；
8. 管理员更新模板后，所有关联用户实例可以获取新版本；
9. Provider API、日志、工作区和请求 dump 不泄露 Key；
10. 旧的普通 Agent、管理员配置的其他模型和现有会话不受影响；
11. SQLite 和 PostgreSQL 迁移都通过；
12. 关键测试和启动验证记录可复现。

## 7. 已确认的外部约束

本阶段已经确认：

1. 智多星调用后端业务或内部系统时，必须带 `chatBizOptions.userid`，用于权限和可读范围校验；
2. ZDX API Key 与 userid 是绑定关系，智多星会校验 Key 和 userid 是否匹配；
3. OA username 是唯一身份标识，使用公司现行的小写拼音规则，冲突时追加数字；
4. 本地改造阶段不接入 OA / 企业微信扫码登录，由管理员手工录入真实 OA username；
5. 初始管理员建议保留现有通用 `general-assistant`，并额外创建“通联发仔”。

仍需在联调时确认的只有接口表现：普通无业务调用的对话请求在缺少 `chatBizOptions.userid` 时，智多星是否接受请求；这不改变第一阶段的安全实现，适配层仍应优先统一注入当前用户身份。

## 8. 本阶段明确不做的技术妥协

- 不用一个全局 ZDX Key 冒充用户级隔离；
- 不把用户 Key 写入全局环境文件；
- 不仅靠前端隐藏按钮实现权限；
- 不用 Agent 名称判断是否为托管 Agent；
- 不用 OA username 生成 Agent ID；
- 不在模板更新时覆盖用户记忆和个人文件；
- 不因为快速上线而允许通联发仔切换到外部模型。
